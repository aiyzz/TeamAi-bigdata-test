# 模型表优化 — 新增数据来源验证

## 触发条件

用户提到以下任一内容时激活本技能：
- 新增数据来源验证、新增来源测试
- 模型表优化测试、结果表增加数据验证
- new data source verification、data source validation

## 适用场景

- **结果表新增数据来源**：ETL 逻辑中新增了一个上游来源表，需要验证新增数据的正确性
- **模型表扩展**：原有模型表增加了新的数据渠道，需要验证新旧数据均正确
- **数据源合并**：多个来源合并到同一结果表，需要验证合并逻辑

## 工作流程

> **【重要】MCP 工具调用说明**
>
> 本 skill 使用 Claude Code 内置的 MCP 工具执行 SQL 查询，无需手动处理 MCP 协议握手。
> 直接调用 `mcp__mysql-server__mysql_query` 等工具即可，Claude Code 框架会自动处理连接和初始化。

### mysql-server MCP 工具列表

| 工具名称 | 功能说明 | 本 skill 用途 |
|----------|----------|---------------|
| `mcp__mysql-server__mysql_query` | 执行 SQL 查询并返回结果 | 执行所有校验 SQL、比对 SQL |
| `mcp__mysql-server__mysql_show_create_table` | 获取表的创建语句（DDL） | Step 0.3 查询表结构，建立知识库 |
| `mcp__mysql-server__mysql_show_columns` | 获取表的列信息 | Step 0.3 备选方案 |

| `mcp__mysql-server__mysql_show_tables` | 获取表列表 | Step 0.3 确认表名 |

### Step 0: 收集信息

#### 0.1 用户提供基础信息

用户只需提供以下最少信息：

| 信息 | 必填 | 说明 |
|------|------|------|
| 生产表名 | 是 | 用于对比的基准表，如 `ytrpt.kcode_crm_ks_dku` |
| 测试表名（结果表名） | 是 | 优化后的表，如 `temp.kcode_crm_ks_dku` |
| ETL 代码 / 产品需求文档 | 是 | SQL 文件或需求文档，用于提取上游表、结果表 |

其余信息通过分析 ETL 代码和表结构自动得出。

#### 0.2 分析 ETL 代码，提取关键信息

从用户提供的 ETL 代码或需求文档中，自动提取以下信息：

**表识别规则**：

- **结果表**：`INSERT INTO` / `INSERT OVERWRITE` 目标表，且不以 `temp.` 开头
- **上游来源表**：`FROM` / `JOIN` 中的表，且不以 `temp.` 开头
- **排除临时表**：`temp.` 开头的中间表不纳入知识库，仅作为代码分析的中间步骤

**提取流程**：

1. **优先从 ETL 代码提取**：阅读用户提供的 SQL 文件，识别 INSERT 语句和 FROM/JOIN 子句，提取所有非临时表名
2. **展示提取结果给用户确认**

#### 0.3 通过 MCP 查询表结构，建立知识库

对 0.2 中提取的每张非临时表，使用 MCP 工具查询表结构并保存为知识库文件。

**查询方式**：

```
mcp__mysql-server__mysql_show_create_table(table="表名", database="库名")
```

若不支持则回退到：

```
mcp__mysql-server__mysql_show_columns(table="表名", database="库名")
```

**知识库文件结构**：

在当前技能位置`dataware_table/` 目录下，每张表生成一个 `[table_name].md` 文件：

```markdown
# [表名]

- **表名**：database.table_name
- **表描述**：从 COMMENT 或需求上下文提取的表用途说明

## 字段列表

| 字段名 | 类型 | 注释 |
|--------|------|------|
| kcode | string | K码 |
| kname | string | K码名称 |
| taking_num | bigint | 快量数 |
| ... | ... | ... |

## 分区信息

- **分区字段**：dt
- **分区格式**：yyyyMMdd

## 索引 / 主键

- **主键**：kcode（若有）
```

**知识库用途**：
- 作为后续测试验证的字段元数据来源
- 供 Step 1（数据质量校验）自动识别维度/指标字段
- 供 Step 5（ETL 转换逻辑验证）获取字段类型和注释
- 跨会话复用，避免重复查询 MCP

> **注意**：MCP 查询结果可能不完整（如 COMMENT 截断、分区信息缺失）。解析后需与用户确认关键信息，不要盲信查询结果。

#### 0.4 自动分析维度字段与指标字段

读取 `dataware_table/` 中已保存的表结构知识库，根据字段类型和 COMMENT 自动分类：

**分类规则**：

| 判断条件 | 分类 |
|----------|------|
| COMMENT 包含枚举值 | 维度字段 |
| COMMENT 包含"数量""金额""快量""指标""统计""汇总"" count""sum""avg"等关键词 | 指标字段 |
| 类型为 INT/BIGINT/FLOAT/DECIMAL 且 COMMENT 不含维度关键词 | 指标字段 |
| 分区字段（dt/rpt_date 等） | 单独归类，不参与维度/指标分类 |

**自动识别分区字段**：
1. 从 DDL 中提取 PARTITION 字段
2. 若无分区定义，优先选择字段名为 `dt` 的字段
3. 其次选择时间类型字段（date/datetime/timestamp）

**自动识别主键**：
1. 从 DDL 中提取 PRIMARY KEY 或 UNIQUE KEY
2. 若无主键定义，查找 COMMENT 中含"主键""唯一"的字段
3. 若均无法确定，询问用户手动指定

#### 0.5 自动打开知识库文档供用户审核

生成知识库文档后，自动打开文档供用户审核：

**操作步骤**：

1. **生成知识库文档**：按 Step 0.3 生成 `dataware_table/` 目录下的表结构文档
2. **自动打开文档**：使用 VSCode 命令打开生成的文档
   ```
   code dataware_table/<table_name>.md
   ```
3. **用户审核**：用户在 IDE 中查看并审核文档内容
4. **提交确认**：用户审核完成后，使用 AskUserQuestion 确认

**确认选项**：
1. 确认，继续执行
2. 调整字段分类（用户可指定哪些字段需要从维度移到指标或反之）
3. 调整主键字段

**注意事项**：
- 每张表生成一个独立的文档文件
- 文档内容包含字段列表、分区信息、主键信息
- 用户可直接在 IDE 中编辑文档进行修正
- 审核完成后再继续后续验证流程

#### 0.6 自动识别分区值

```sql
SELECT MAX(dt) AS latest_dt
FROM <测试表>
WHERE dt >= DATE_FORMAT(DATE_SUB(CURDATE(), INTERVAL 7 DAY), '%Y%m%d')
```

若查询成功且返回非空值 → 使用该日期作为分区时间
若查询失败或返回空值 → 询问用户手动提供分区日期

### Step 1: 数据质量校验

> **目的**：在对比新旧表之前，先确认测试表自身的数据质量。
> **SQL 模板**：详见 [quality-check-sql.md](quality-check-sql.md)

#### 1.1 维度字段校验

从 `dataware_table/` 知识库读取维度字段列表，按 [quality-check-sql.md](quality-check-sql.md) 中的模板依次执行：

1. **主键唯一性**：检查主键是否有重复记录，预期 0 条
2. **空值占比**：对每个维度字段 UNION ALL 批量执行，空值占比 > 5% 标记警告
3. **维度值分布 TOP 20**：对关键维度字段各执行一次，单值占比 > 50% 标记警告
4. **枚举值校验**：对枚举字段（如 first_tab_type, sum_type）检查取值范围，预期外取值即异常

#### 1.2 指标字段校验

从 `dataware_table/` 知识库读取指标字段列表，按 [quality-check-sql.md](quality-check-sql.md) 中的模板依次执行：

1. **空值和零值占比**：空值+零值占比 > 30% 标记警告
2. **统计分布**：计算 MIN/MAX/AVG/MEDIAN，MIN < 0 对数量金额类字段标记异常
3. **范围校验**：仅对 COMMENT 含"数量""金额"的字段执行，invalid_cnt > 0 即异常

#### 1.3 输出数据质量报告

汇总校验结果，按 [quality-check-sql.md](quality-check-sql.md) 中的异常判定标准标记状态：

| 状态 | 标记 | 含义 |
|------|------|------|
| ❌ FAIL | ❌ | 严重问题（主键重复/空值、枚举异常、指标负值） |
| ⚠️ WARN | ⚠️ | 警告项（维度空值>5%、单值占比>50%、指标空零值>30%） |
| ✅ PASS | ✅ | 通过 |

#### 1.4 空表前置检查

在进入数据量对比前，先检查两张表是否有数据：

```sql
SELECT '测试表' AS tbl, count(*) AS cnt FROM <测试表> WHERE dt = '<分区值>'
UNION ALL
SELECT '生产表' AS tbl, count(*) AS cnt FROM <生产表> WHERE dt = '<分区值>'
```

**边界处理**：

| 情况 | 处理 |
|------|------|
| 测试表 = 0，生产表 = 0 | 终止，提示"两张表均无数据，无法验证" |
| 测试表 = 0，生产表 > 0 | 终止，提示"测试表为空，数据丢失" |
| 测试表 > 0，生产表 = 0 | 提示"生产表为空，跳过对比，仅做数据质量校验"，跳过 Step 2-4 |
| 两张表均 > 0 | 继续执行 Step 2 |

### MCP 执行与错误处理

**默认使用 MCP 自动执行**。仅当 MCP 服务不可用时，回退到手动执行方式。

#### 方式 1：MCP 自动执行（默认）

**自动获取分区日期**：

自动识别分区字段并查询近 7 天的最大分区日期，无需询问用户：

```sql
SELECT MAX(<partition_field>) AS latest_dt
FROM <table_name>
WHERE <partition_field> >= DATE_FORMAT(DATE_SUB(CURDATE(), INTERVAL 7 DAY), '%Y%m%d')
  AND <partition_field> <= DATE_FORMAT(CURDATE(), '%Y%m%d')
```

- 若查询成功且返回非空值 → 使用该日期作为分区时间
- 若查询失败或返回空值 → 回退询问用户手动提供分区日期和分区字段

**执行 SQL**：

直接调用 Claude Code 内置的 MCP 工具执行 SQL：

```
mcp__mysql-server__mysql_query(query="<SQL语句>")
```

**执行报错时的自动修复循环**（最多 3 次）：
1. 阅读错误信息，分析原因（语法错误、字段不存在、表不存在等）
2. 修改 SQL
3. 重新调用 `mcp__mysql-server__mysql_query` 执行
4. 若仍报错，重复 1-3
5. 若 3 次修复后仍失败，向用户展示错误信息

#### 方式 2：手动复制 SQL 执行（MCP 不可用时的回退）

当 MCP 服务不可用（连接失败、工具调用报错等）时，自动回退到此方式：

1. 告知用户 MCP 服务不可用，切换到手动执行模式
2. 向用户展示生成的完整 SQL，可直接复制执行
3. 提示用户替换分区变量 `${dt}` 为实际日期值

### Step 6: 生成测试报告

> **【重要】报告必须附带完整 SQL 明细**
>
> 报告的每个验证步骤必须附带实际执行的 SQL 语句，确保验证过程可追溯、可复现。
> SQL 明细放在报告末尾的附录部分，按验证步骤分类组织。
>
> **每条 SQL 必须标注对应的测试点**，格式为：`> 测试点：X.Y 测试项名称`
> 放在 SQL 代码块之前，确保读者能快速定位每条 SQL 验证的具体内容。
>
> **每条 SQL 必须附带实际执行结果**，格式为：
> ```sql
> -- 执行结果：
> -- | total_cnt | distinct_cnt | dup_cnt |
> -- |-----------|--------------|---------|
> -- | 3638      | 3638         | 0       |
> ```
> 将查询返回的 JSON 结果转为 Markdown 表格，嵌入 SQL 代码块末尾的注释中。


## 注意事项

- 大表务必加分区条件，避免全表扫描
- 临时表使用后及时清理：`DROP TABLE IF EXISTS temp.tmp_xxx`
- 来源表过滤条件必须与 ETL 代码中的 WHERE 子句保持一致
- 转换逻辑验证需要先阅读 ETL 代码，梳理出每个字段的转换规则，再逐一生成验证 SQL
- 若验证发现差异，需区分是 ETL 逻辑 bug 还是上游数据问题
