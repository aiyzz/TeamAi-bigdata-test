# 数据验证技能（对话式）

## 目录结构

```
.claude/skills/data-verify/
├── skill.md                    # 技能主文件（本文件）
├── capabilities/               # 原子能力定义（从 atomic-data-verify 继承）
├── templates/                  # SQL 模板（从 atomic-data-verify 继承）
├── knowledge/                  # 知识沉淀（从 atomic-data-verify 继承）
└── report/                     # 验证报告（按日期归档）
    └── {YYYY-MM-DD}/
        ├── {table_name}_verify.sql      # 验证 SQL 脚本（DBeaver 可直接执行）
        ├── {table_name}_sql_draft.md    # SQL 初稿（Step 3 生成，审核前）
        ├── {table_name}_sql_merged.md   # 合并后的可执行 SQL（Step 3/4 产出）
        ├── {table_name}_sql_audit.md    # SQL 审核报告（Step 4）
        └── {table_name}_report.md       # 验证报告（Step 6）
```

## 流程总览（6 步对话式）

| Step | 说明 | 交互方式 |
|------|------|----------|
| 1 | 收集信息 | 一次性收集所有必要信息 |
| 2 | 能力判别 + 确认 | 数据驱动判别 + 用户确认 |
| 3 | 生成 SQL | 一次性生成所有 SQL |
| 4 | SQL 审核 | 自动审核 SQL 是否符合模板 |
| 5 | 用户执行 + 反馈 | 用户粘贴执行结果 |
| 6 | 生成报告 + 知识沉淀 | 自动生成报告 |

## Step 1: 信息收集（表单式）

### 1.1 生成调研表单（HTML 可编辑表单）

触发验数技能后，**必须使用 HTML 可编辑表单**收集信息（用户在输入框直接填写，禁止使用 markdown 模板或 AskUserQuestion 逐轮追问）：

1. **复制模板**：将 `templates/survey-form.html` 复制到工作目录（如 `report/{YYYY-MM-DD}/` 或当前 workspace）。
2. **预填表名**：若用户在触发指令中已给出生产表/测试表名，编辑 HTML 中对应 `<input>` 的 `value` 属性预填并加上 `prefilled` 样式类高亮；也可通过 URL 参数预填：`survey-form.html?pro_table=库.表&test_table=库.表`。
3. **打开表单**：使用以下方式打开 HTML 文件（按优先级）：
   - **present_files**：若环境支持，用 `present_files` 打开会在预览面板渲染为可填写表单
   - **浏览器打开**：执行 `start "" "path/to/survey-form.html"`（Windows）或 `open "path/to/survey-form.html"`（macOS）在默认浏览器中打开
   - **VSCode 预览**：执行 `code --preview "path/to/survey-form.html"` 在 VSCode 内预览
4. **用户填写**：用户在各输入框直接填写（DDL 直接粘贴 `SHOW CREATE TABLE` 输出），填完点击底部「📋 复制填写结果」按钮 —— 自动校验必填项并把内容格式化为 markdown 复制到剪贴板。
5. **回传**：用户将剪贴板内容粘贴回对话，进入 Step 1.3 解析。

> **禁止降级**：不允许退回 markdown 模板或使用 AskUserQuestion 逐轮追问。HTML 表单是唯一的信息收集方式。

> **模板字段说明**见 Step 1.2；HTML 表单字段与 markdown 模板完全对应。

### 1.2 表单字段说明

| 编号 | 字段 | 必填 | 用途 |
|------|------|------|------|
| 1 | 需求/ETL说明 | 是 | Layer 1 能力判别 + ETL逻辑提取（能力2/3来源追溯） |
| 2-3 | 生产表名/测试表名 | 是 | 基础验证信息 |
| 4 | 分区字段及分区值 | 是 | 所有SQL的分区条件 |
| 5-6 | 生产表DDL/测试表DDL | 是 | 字段自动分类 + 能力1字段比对 + 能力4字段增减 |
| 7 | 主键字段 | 否 | JOIN键。不填则模型根据DDL识别候选主键，用AskUserQuestion确认 |
| 8-9 | 测试表/生产表记录数 | 否 | Layer 2 能力判别。不填则生成记录数统计SQL由用户执行后反馈 |

### 1.3 解析与补问

用户回复表单后，按以下流程解析：

1. **提取基础信息**：表名、分区字段、分区值
2. **解析DDL**：字段自动分类（见 1.5）
3. **主键处理**：
   - 已填写 → 直接使用
   - 未填写 → 模型根据DDL识别候选主键（优先选择含"code"/"id"/"key"的字段）→ 用 AskUserQuestion 确认
4. **需求分析**：从需求描述提取关键词，用于 Layer 1 能力判别（见 Step 2.1）
5. **数据量处理**：
   - 已填写 → 用于 Layer 2 能力判别（见 Step 2.2）
   - 未填写 → 仅依赖 Layer 1 判别，记录数统计SQL作为主流程 [1.2] 由用户执行后反馈

### 1.4 表结构获取（DDL优先级）

用户在表单中提供的DDL优先级最高。若用户未提供完整DDL：
1. 从知识库读取 `knowledge/table/{database}.{table}/schema.md`
2. 追问用户提供 DDL（SHOW CREATE TABLE 输出）

### 1.5 字段自动分类

从 DDL 提取字段后，按以下规则分类：

| 判断条件 | 分类 |
|----------|------|
| COMMENT 包含枚举值描述 | 维度 |
| COMMENT 含"数量""金额""指标""统计""汇总""count""sum""avg" | 指标 |
| 类型为 INT/BIGINT/FLOAT/DECIMAL 且 COMMENT 不含维度关键词 | 指标 |
| 分区字段（dt/rpt_date 等） | 分区 |
| 其余 | 维度 |

## Step 2: 能力判别 + 确认

### 2.1 Layer 1 — 需求文档分析（优先级最高）

阅读用户提供的需求文档/ETL代码，提取关键词：

| 需求关键词 | 激活能力 |
|-----------|---------|
| 新增数据来源、扩展、新数据源、增加数据 | 能力2（验证增加记录） |
| 剔除、筛选条件、过滤、减少、移除数据 | 能力3（验证减少记录） |
| 迁移、双写、一致性、比对 | 能力1（验证不变更记录） |
| 增加字段、删除字段、新增列、结构变更 | 能力4（验证字段增减） |
| 优化需求（无明确增减描述） | 能力1 + 能力2（默认组合） |

### 2.2 Layer 2 — 数据验证（基于用户提供的信息）

根据 Step 1.2 用户提供的数据量信息，修正 Layer 1 的判断：

| 用户提供的信息 | 判断条件 | 激活能力 |
|---------------|----------|----------|
| 测试表记录数 > 生产表记录数 | `added_cnt > 0` | 确认激活能力2 |
| 测试表记录数 < 生产表记录数 | `removed_cnt > 0` | 确认激活能力3 |
| 测试表字段数 > 生产表字段数 | 新增字段 | 确认激活能力4（D1/D3） |
| 测试表字段数 < 生产表字段数 | 删除字段 | 确认激活能力4（D2） |
| 用户明确列出新增字段 | 字段名列表 | 确认激活能力4 |
| 两表记录数一致 | `added = 0, removed = 0` | 仅激活能力1 |
| 无生产表（新增表场景） | - | 激活能力6 |

**与 Layer 1 矛盾时**：提醒用户确认，以数据为准。

### 2.3 能力激活清单

展示给用户确认：

| 能力 | 激活原因 | 状态 |
|------|----------|------|
| 能力0: 数据质量检查 | 始终执行 | ✅ |
| 能力5: SQL 审核 | 始终执行（Step 4） | ✅ |
| 能力1: 验证不变更记录 | 需求文档 / 记录数一致 | ✅ / ⬜ |
| 能力2: 验证增加记录 | 需求文档 / 测试表记录数 > 生产表 | ✅ / ⬜ |
| 能力3: 验证减少记录 | 需求文档 / 测试表记录数 < 生产表 | ✅ / ⬜ |
| 能力4: 验证字段增减 | 需求文档 / 字段数差异 | ✅ / ⬜ |
| 能力6: 基准表溯源验证 | 新增表场景 / 需求文档提及基准表 | ✅ / ⬜ |

### 2.3 ETL 逻辑确认（能力2/4 必填）

当激活能力2或能力4时，需要确认ETL逻辑。优先从表单「需求/ETL说明」（字段1）中提取，缺失项用 AskUserQuestion 补问。

**提取流程**：
1. 从需求描述中提取源表名称、关联键、筛选条件
2. 缺失项用 AskUserQuestion 追问（单轮最多4题）

**源表信息**：
| 确认项 | 说明 | 示例 | 提取来源 |
|--------|------|------|----------|
| 源表名称 | 新增数据的来源表 | `nike.ods_jsc_t_market_direct_customer_dd` | 需求描述提取 / AskUserQuestion |
| 关联键 | 测试表与源表的关联字段 | `测试表.kcode = 源表.k_code` | 需求描述提取 / AskUserQuestion |
| 筛选条件 | 从源表筛选数据的条件 | `settle_code LIKE 'ZK%'` | 需求描述提取 / AskUserQuestion |

**字段映射**（能力4激活时）：
| 确认项 | 说明 | 示例 |
|--------|------|------|
| 源字段 | 源表中的字段名 | `sales_emp_code` |
| 目标字段 | 测试表中的字段名 | `sale_emp_code` |
| 转换类型 | 直接映射 / ETL转换 | 直接映射 |
| 转换逻辑 | ETL转换的表达式（如有） | `CASE WHEN status='1' THEN '有效' ELSE '无效' END` |

**触发条件**：
- 新增表场景（无生产表可对比）
- 需求文档中提及基准表

**自动匹配基准表**：

| 揽收、收件 | dwd.waybill_take_waybill_info_dd |

**口径判断规则**：

## Step 3: 生成 SQL

### 3.1 生成流程

1. 读取激活能力清单
2. 读取 ETL 逻辑确认
3. 读取对应 SQL 模板
4. 替换占位符
5. 写入 `report/{YYYY-MM-DD}/{table_name}_verify.sql`
6. 在对话中展示 SQL 列表

> **宽表增量预览**：字段数 > 20 时，UNION ALL 批量比对 SQL 较长，生成过程中边输出边在对话展示进度（如"已生成 X/Y 个字段比对"），避免用户长时间无反馈。

### 3.2 SQL 脚本格式

生成 `.sql` 文件，使用 DBeaver **Alt+X（执行脚本）** 一次性执行，每条 SELECT 结果显示在独立标签页。

```sql
-- ============================================================
-- 数据验证 SQL 脚本
-- 生产表: {database}.{table_name}    测试表: {database}.{table_name}
-- 分区值: {dt_value}    主键: {primary_key}
-- 执行方式: DBeaver → Alt+X (执行脚本)
-- ============================================================

-- ============================================================
-- 主流程
-- ============================================================

-- [1.1] 空表前置检查
{SQL内容};

-- [1.2] 数据量统计
{SQL内容};

-- [1.3] 字段结构比对
{SQL内容};

-- ============================================================
-- 能力0: 数据质量检查
-- ============================================================

-- [0.1] 主键唯一性
{SQL内容};

-- [0.2] 维度字段空值占比
{SQL内容};

-- [0.3] 指标字段空值+零值占比
{SQL内容};

-- [0.4] 枚举值校验
{SQL内容};

-- ============================================================
-- 能力1: 不变更记录验证
-- ============================================================

-- [1.1] 共同记录数
{SQL内容};

-- [1.2] 批量字段差异数
{SQL内容};

-- ============================================================
-- 能力2: 增加记录验证
-- ============================================================

-- [2.1] 来源追溯匹配
{SQL内容};

-- [2.2] 筛选条件符合性
{SQL内容};

-- [2.3] 不符合条件排查
{SQL内容};

-- [2.4] 新增记录特征明细
{SQL内容};
```

**格式规范**：
- 每条 SQL 以分号 `;` 结尾（DBeaver 执行脚本要求）
- 每条 SQL 前有 `-- [编号] 说明` 注释
- 每条 SQL 后有 `-- 预期: xxx` 注释说明预期结果
- 区块间用 `-- ===` 分隔线区分能力
- 头部注释包含基础信息（表名、分区值、主键、执行方式）

### 3.3 占位符替换规则

| 占位符 | 替换为 | 来源 |
|--------|--------|------|
| `<测试表>` | `database.table_name` | Step 1 |
| `<生产表>` | `database.table_name` | Step 1 |
| `<主键>` | `kcode` | Step 1 |
| `<分区值>` | `20260727` | Step 1 |
| `<field>` | 实际字段名 | 知识库 schema.md |
| `<维度字段列表>` | UNION ALL 所有维度字段 | 知识库 schema.md |
| `<指标字段列表>` | UNION ALL 所有指标字段 | 知识库 schema.md |
| `<共同字段列表>` | UNION ALL 所有共同字段 | 知识库 schema.md |
| `<上游表>` | `database.table_name` | Step 2 |
| `<关联键>` | `t.kcode = src.k_code` | Step 2 |
| `<筛选条件>` | `settle_code LIKE 'ZK%'` | Step 2 |
| `<源字段>` | `sales_emp_code` | Step 2 |
| `<目标字段>` | `sale_emp_code` | Step 2 |
| `<转换表达式>` | `CASE WHEN ... END` | Step 2 |

## Step 4: SQL 审核

### 4.1 审核流程

1. 读取 Step 3 生成的 `.sql` 文件
2. 读取对应的 SQL 模板文件
3. 逐条审核 SQL 是否符合模板规范
4. 修正偏差（直接修改 `.sql` 文件）
5. 生成审核报告

### 4.2 审核内容

引用 `capabilities/cap-5-sql-audit.md`，执行：

**通用检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 分区条件声明 | 所有 SQL 包含 `dt = '<分区值>'` | 缺少分区条件 |
| 表名完整 | 使用 `database.table_name` 格式 | 表名不完整 |
| 主键正确 | JOIN 条件使用正确的主键 | 主键字段错误 |

**能力0检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 空表前置检查 | 同时检查测试表和生产表 | 只检查单表 |
| 主键唯一性 | `GROUP BY <主键> HAVING count(*) > 1` | 结构错误 |
| 维度空值占比 | `UNION ALL` 批量执行所有维度字段 | 未批量或字段遗漏 |
| 指标空值+零值占比 | `UNION ALL` 批量执行所有指标字段 | 未批量或字段遗漏 |

**能力1检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 字段比对 NULL 处理 | 使用三段式 | 缺少 NULL 处理 |
| 字段比对批量 | 使用 `UNION ALL` 批量执行 | 未批量或字段遗漏 |
| 共同记录数 | 使用 `INNER JOIN` 统计 | JOIN 类型错误 |

**能力2检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 来源追溯匹配 | 使用 `NOT EXISTS` 子查询 | 未使用 EXISTS 结构 |
| 筛选条件符合性 | 使用 `NOT EXISTS` + `CASE WHEN` | 未使用 EXISTS 或 CASE WHEN |

**能力3检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 剔除逻辑验证 | 使用 `NOT EXISTS` 子查询 | 未使用 EXISTS 结构 |
| 误删排查 | 包含误删明细查询 | 缺少排查查询 |

**能力4检查**：
| 检查项 | 预期 | ❌ FAIL 条件 |
|--------|------|-------------|
| 原有字段保护 | 使用三段式 NULL 处理 | 缺少 NULL 处理 |
| 新增字段验证（直接映射） | 使用 `NVL(CAST(... AS STRING), '')` 包裹 | 缺少 NULL 安全处理 |
| 新增字段验证（ETL 转换） | 使用 `NVL(CAST(<转换表达式> AS STRING), '')` 包裹 | 缺少 NULL 安全处理 |

### 4.3 审核输出

生成 `report/{YYYY-MM-DD}/{table_name}_sql_audit.md`：

```markdown
# SQL 审核报告

## 审核概要

| 项目 | 内容 |
|------|------|
| 审核时间 | YYYY-MM-DD |
| 激活能力 | 能力0, 能力1, 能力2, ... |
| 审核SQL数量 | N 条 |
| 通过数量 | M 条 |
| 偏差数量 | K 条 |

---

## 审核结果

| 测试点 | SQL 类型 | 是否遵循模板 | 修正说明 |
|--------|----------|-------------|----------|
| 0.1 | 空表前置检查 | ✅ 是 | - |
| 0.2 | 主键唯一性 | ✅ 是 | - |
| 1.1 | 字段比对 | ❌ 否 | 已修正：补充完整UNION ALL |
| ... | ... | ... | ... |

**审核结论**：全部通过 / 存在 N 处偏差已修正

---

## 审核通过的 SQL

（修正后的完整SQL，按能力分组）
```

### 4.4 审核标准

| 结果 | 状态 | 后续动作 |
|------|------|----------|
| 所有 SQL 符合模板 | ✅ PASS | 继续执行 Step 5 |
| 部分 SQL 存在偏差 | ⚠️ WARN | 修正后继续执行 |
| 关键 SQL 结构错误 | ❌ FAIL | 重新生成SQL脚本 |

## Step 5: 用户执行 + 反馈

### 5.1 执行指引

告知用户：
1. 使用 DBeaver 打开 `{table_name}_verify.sql` 文件
2. **Alt+X（执行脚本）** 一次性执行所有 SQL
3. 结果在下方多个标签页中依次展示
4. 将结果截图或描述关键数据回来（如"全部为 0 / 无异常"）

### 5.2 结果解析

用户粘贴结果后，AI 解析：
- 提取关键数值（记录数、差异数、空值占比等）
- 判断是否异常（对比阈值）
- 判断是否需要补充信息

### 5.3 异常处理

| 场景 | 处理 |
|------|------|
| 用户粘贴的结果格式不清晰 | 请用户重新粘贴或描述关键数据 |
| SQL 执行报错 | 分析错误原因，修正 SQL |
| 结果异常需要补充验证 | 生成补充 SQL |
| 分区不存在（Partition not found） | 先 `SHOW PARTITIONS <表>` 确认分区值，让用户改用正确分区或等 ETL 重跑 |
| 权限不足 / 表不存在 | 提示用户确认表名与库权限，必要时换库或申请权限 |
| 字段名不匹配 / 字段不存在 | 核对 schema，修正占位符字段名后重新生成 |
| NULL 与空串误判 | 确认是否按字段类型套用 NULLIF/NVL 归一化（见 sql-patterns.md），数值字段去掉 NULLIF |
| 数据量超预期（JOIN 膨胀 / 笛卡尔积） | 检查 JOIN 键是否唯一，子查询先去重（见 verify-rules.md JOIN 膨胀防护） |
| 执行超时 / 数据倾斜 | 大表加分裁剪与主键过滤，记录数 > 1000 万时分批验证 |

## 通用注意事项

- 大表务必加分区条件，避免全表扫描
- 哨兵值 `'XXT'` 应选择业务数据中不会出现的值
- NULL 和空字符串统一归一化为 `'XXT'`，避免 `NULL = NULL` 误判
- 临时表使用后及时清理
